# Agent trust and developer workflow direction — 2026-11-05

Status: researched proposals, not an implementation commitment or product rename.
Sources were retrieved on 2026-11-05. Current documentation is not proof of an
installed version's behavior. No competitor executable, provider/model, live
remote endpoint or new native-client integration was tested for this research.

## Recommended direction

Extend mcpm toward **local agent trust evidence and change review**, using its
existing configuration readers, drift/integrity primitives, versioned evidence and
measured MCP runtime guard. Start with the confirmed wrapper-identity defect
**#155**, then read-only project visibility **#141**. Test a small local skill/plugin
change-review receipt **#156** with one consumer before building a broader product.
Managed-policy compatibility **#122** is a safety prerequisite for wrapping in
managed environments. This direction is an engineering/product inference; demand
and willingness to adopt it have not been measured.

A broader artifact report must distinguish declared, present, cached,
observed-loaded and enforced state. A config file or successful static check does
not establish activation, permission enforcement or safety. Keep the current MCP
CLI/package identity while testing the additional use case; reconsider branding
or architecture only after the experiment produces repeat use.

[Code review PR #308](https://github.com/getmcpm/cli/pull/308) separately addresses
reproduced config/store/lock/scanner/SRI/reporting defects and reconciles existing
docs. Those changes merged and are included in the v0.49.1 release preparation.
The [backlog](BACKLOG.md) separates them,
existing unfinished work and new proposals.

## Build order and decision gates

1. **Correctness first:** review/merge the tested fixes through the normal gate;
   release only on a separate instruction. Fix #155 with an explicit launch-form
   compatibility matrix, including ambiguous/malformed legacy forms. Do not add
   protection claims while plain entries can receive guarded status.
2. **Small DevX improvement:** extend #141 with an explicit project root and
   target host profile. Produce read-only scope/coverage evidence before adding
   project mutation. Preserve #131 unknown/unreadable reporting and #122 managed
   restrictions; unavailable state never means absent or permitted.
3. **First beyond-MCP experiment:** #156 compares two supplied local snapshots
   for Agent Skills plus one Claude plugin dialect. Report changed bytes, sources,
   instruction/resource references and execution-bearing declarations. Review
   feedback from one real consumer decides whether to continue. No download,
   install, script execution, permission grant or automatic activation.
4. **Conditional integrations:** #157 accepts one already-produced, versioned
   external report bound to an exact digest. Keep original analysis mode,
   incomplete/error state and tool attribution. #158 measures one native plugin
   activation lifecycle only if #156 needs loaded-state proof.
5. **Later, demand-gated:** finish the retained-manifest portion of #140 with
   pinned beta fixtures; #95 remains an isolation/breakage experiment. #159 is an
   offline ACP evidence spike, not a committed new runtime carrier. A2A is watch
   only until a concrete workflow appears.

The acceptance criteria, dependencies, effort judgments and non-goals live in

## Scope and stop rules

Do not build a marketplace, generic plugin/skill installer, general scanner,
enterprise control plane, browser firewall, delegation/identity broker, task
scheduler, live ACP/A2A proxy or remote HTTP/OAuth guard merely to match a trend.
Do not invent a universal safety score or represent a hash/manifest as publisher
identity, loaded-state proof or compliance. Existing scanners/native controls may
be better integrations than new security-critical code.

Before expanding #156, require one identifiable consumer and a concrete update
review it helps decide. Stop or integrate an existing tool if that consumer gets
the same answer from native/APM tooling with less effort. Before live scanner or
model evaluation, require an explicit execution, data-egress and provider-budget
scope. Demand, false-positive improvement, performance, token savings and market
size were not measured here; no old adoption/kill criterion is reset.

Method: three Astra research lenses (standards, security/overlap, portfolio/DevX),
current repo/backlog deduplication and parent primary-source cross-checks. Public
pages are untrusted research data. Conflicting maturity descriptions and
unmeasured vendor claims remain visible rather than becoming implementation facts.
